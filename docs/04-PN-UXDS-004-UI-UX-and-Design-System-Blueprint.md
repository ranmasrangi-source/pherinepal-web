## 1. DOCUMENT PURPOSE
This document defines the official user interface (UI), user experience (UX), visual identity application, website structure, navigation system, design components, responsive behaviour and interaction standards for PHERI NEPAL.

It translates the functional requirements established in Document 03 into a consistent, accessible and professional website design system.

The design must communicate:
- Trust and reliability.
- Nepal's tourism identity.
- Professionalism.
- Simplicity and clarity.
- International usability.
- Cultural respect.
- Easy access to tourism information and services.

This document governs how the platform looks, how users navigate it, how interface elements behave and how design consistency is maintained.
It does not redefine project scope, revenue rules, booking policies, technical architecture or operational permissions.

## 3. DESIGN VISION
PHERI NEPAL must look and feel like a trusted national tourism platform rather than a simple travel blog or ordinary business directory.

The design should combine:
- A premium tourism presentation.
- Clear information architecture.
- Strong destination imagery.
- Simple service discovery.
- Consistent business listings.
- Understandable inquiry processes.
- Helpful AI interaction.
- Reliable multilingual navigation.

The visual experience should be modern and distinctive without becoming complicated or excessively decorative.

### 3.1 Core Design Principles
| Principle | Design Requirement |
| :--- | :--- |
| Trust First | Clear information, transparent labels and consistent presentation |
| Simple Navigation | Users should understand where to go and what to do |
| Mobile First | Core journeys must work well on mobile screens |
| Visual Discovery | Destination imagery should support exploration |
| Consistency | Reusable components across the website |
| Accessibility | Readable, understandable and usable interfaces |
| Transparency | Paid placements and sponsored material must be identified |
| Cultural Respect | Nepal's cultural and geographic diversity must be represented accurately |
| Performance Awareness | Avoid unnecessarily heavy visual elements |
| Scalability | Design patterns must support future platform expansion |

## 5. TYPOGRAPHY SYSTEM
Typography must remain readable across English, Nepali and the other supported languages.

### 5.1 Font Requirements
The selected typefaces must support:
- Latin characters.
- Devanagari characters.
- Nepali text rendering.
- International language requirements.
- Consistent weight and spacing.
- Readable mobile presentation.

### 5.2 Recommended Typography Direction
| Typography Role | Recommended Direction |
| :--- | :--- |
| English Interface | Clean modern sans-serif |
| Nepali Interface | High-quality Devanagari-compatible sans-serif |
| Headings | Strong, readable sans-serif weights |
| Body Text | Regular-weight readable sans-serif |
| Buttons | Medium or semibold |
| Metadata | Smaller but legible text |
| Numbers and Status Data | Clear, consistent numeric presentation |

Inter may be used as an English interface font candidate, with Noto Sans Devanagari as a Devanagari font candidate.
The final font selection must be checked for all approved languages before production.

### 5.3 Typography Hierarchy
The website should maintain a consistent hierarchy:
1. Main page heading.
2. Section heading.
3. Subsection heading.
4. Card title.
5. Body text.
6. Supporting description.
7. Metadata and labels.

Typography must not rely on excessively small text to fit more information on a screen.

### 16.2 Multilingual Layout Behaviour
The design system must account for:
- Different text lengths.
- Devanagari rendering.
- Font fallback.
- Navigation expansion.
- Button text expansion.
- Form label length.
- Different line wrapping.
- Consistent spacing.
- Language-specific typography.

### 16.3 Translation Quality
- Important interface labels must be professionally translated or reviewed.
- Machine translation must not be treated as automatically approved.
- Critical travel information must receive appropriate quality review.
- Missing translations must have a clear fallback treatment.
- Mixed-language interface fragments should be avoided wherever possible.

The final language list remains governed by Document 01 and the approved source-market research.

## 17. RESPONSIVE DESIGN SYSTEM

### 17.1 Responsive Design Priorities
**Mobile**
- Compact navigation.
- Readable text.
- Clear primary actions.
- Touch-friendly controls.
- Simplified card layouts.
- Forms designed for small screens.

**Tablet**
- Balanced content width.
- Flexible card grids.
- Clear navigation.
- Appropriate spacing.

**Desktop**
- Full navigation.
- Multi-column content where useful.
- Larger image presentation.
- Efficient dashboard layouts.
- Clear information hierarchy.

### 17.2 Responsive Behaviour
The layout should adapt without:
- Horizontal overflow.
- Overlapping text.
- Hidden essential actions.
- Unusable forms.
- Distorted images.
- Inaccessible navigation.

The final breakpoints must be established during implementation and tested against real devices and screen sizes.

## 19. DESIGN TOKENS AND SPACING
The design system should use centrally managed design tokens rather than unrelated values across individual pages.

### 19.1 Spacing Scale
A consistent spacing scale should be adopted for:
- Component padding.
- Card spacing.
- Section spacing.
- Form field gaps.
- Navigation spacing.
- Page margins.

The implementation may use a base spacing unit and consistent multiples of that unit.

### 19.2 Border and Radius System
The interface should use a limited set of:
- Border widths.
- Border colours.
- Corner radius values.
- Divider styles.

Excessive rounded cards and decorative borders should be avoided.

### 19.3 Shadow System
Shadows should be subtle and used only when they improve visual hierarchy.
The website should not rely on heavy shadows to separate every element.

### 19.4 Iconography
Icons should be:
- Consistent in style.
- Understandable.
- Used with labels where meaning is not obvious.
- Appropriate for tourism and platform functions.
- Accessible to assistive technologies where relevant.

## 20. INTERACTION AND FEEDBACK STANDARDS
Every interactive element must provide understandable feedback.

### 20.1 Button States
Buttons should support:
- Default.
- Hover where applicable.
- Focus.
- Active.
- Loading.
- Disabled.

### 20.2 Form States
Forms should support:
- Empty.
- Focused.
- Filled.
- Invalid.
- Submitting.
- Successful.
- Failed.

### 20.3 Loading States
Loading indicators should appear when an action requires processing.
Examples include:
- Search results loading.
- Destination information loading.
- Inquiry submission.
- AI response generation.
- Partner dashboard loading.

### 20.4 Empty States
Empty states should explain what is missing and provide a relevant next action where possible.
Examples:
- No destinations found.
- No saved destinations.
- No booking inquiries.
- No partner listings.
- No notifications.

### 20.5 Confirmation and Error Feedback
Important actions should provide clear confirmation or error feedback.
The interface must not show success until the system has actually reported success.

## 21. ACCESSIBILITY REQUIREMENTS
The website should follow recognized accessibility principles, using WCAG 2.2 Level AA as the design target where applicable.
The interface should support:
- Adequate text contrast.
- Keyboard navigation.
- Visible focus indicators.
- Accessible form labels.
- Descriptive link text.
- Appropriate image alternative text.
- Clear error identification.
- Logical heading structure.
- Screen-reader-friendly interaction patterns.
- Readable text sizing.
- Touch-friendly controls.

Accessibility must be considered during design and implementation, not added only at the final testing stage.

- Destination cards.

## 31. VERSION 2.0 DESIGN SYSTEM ENGINEERING SPECIFICATIONS & AUDIT GAP RESOLUTIONS

### 31.1 Bilingual & 12-Language Typography Tokens (Devanagari Clipping Prevention)
To prevent vertical clipping of Devanagari vowel diacritics (*matras* such as ी, े, ै, ो, ौ, ँ) and ensure crisp legibility across Latin (`Inter`) and Devanagari (`Noto Sans Devanagari`) scripts:

| Typography Token | Latin (`en-US`, `fr-FR`, `de-DE`, `es-ES`) | Devanagari (`ne-NP`, `hi-IN`) & CJK/Thai | Mandatory CSS / Layout Rule |
| :--- | :--- | :--- | :--- |
| **Display Hero (`H1`)** | `font-size: 2.75rem (44px)`, `line-height: 1.18`, `letter-spacing: -0.02em` | `font-size: 2.5rem (40px)`, `line-height: 1.42`, `letter-spacing: 0em` | Never apply `overflow-hidden` with tight fixed height on headings; add `padding-top: 0.08em`. |
| **Section Heading (`H2`)** | `font-size: 2rem (32px)`, `line-height: 1.25` | `font-size: 1.875rem (30px)`, `line-height: 1.48` | Use dynamic `lang` attribute selector (`:lang(ne)`, `:lang(hi)`) to automatically widen `line-height`. |
| **Card Title (`H3`)** | `font-size: 1.25rem (20px)`, `line-height: 1.35` | `font-size: 1.25rem (20px)`, `line-height: 1.55` | Line-clamp containers (`line-clamp-2`) must reserve `min-height: 3.1em` in Devanagari. |
| **Body Default** | `font-size: 1rem (16px)`, `line-height: 1.6` | `font-size: 1.03rem (16.5px)`, `line-height: 1.78` | Minimum body font size on mobile is strictly `16px` to prevent iOS auto-zoom and eye strain. |
| **Badge / Metadata** | `font-size: 0.75rem (12px)`, `line-height: 1.3`, `uppercase` | `font-size: 0.8125rem (13px)`, `line-height: 1.5`, `normal-case` | Disable `text-transform: uppercase` and positive `letter-spacing` when rendering Devanagari, Arabic, Thai, or CJK scripts. |

### 31.2 Mobile-First Partner Workspace Standard (`U03` Business Partner Portal)
Because over 80% of local homestay hosts, licensed trekking guides, jeep operators, and regional hotel owners in Nepal manage operations from Android smartphones on cellular connections:
1. **Thumb-Friendly Mobile Partner Action Bar (`360px–767px`):**
   - The Partner Dashboard (`M12`) must NOT require a desktop monitor to respond to inquiries (`M07`), update availability, or upload verification documents (`ENT-017`).
   - Incoming booking inquiries must render as swipe/tap cards with minimum `48px x 48px` primary action buttons: **`[Confirm Availability]`**, **`[Send Counter-Offer / Reply]`**, and **`[Mark Unavailable]`**.
2. **Direct Smartphone Camera KYC Upload:**
   - Document verification upload (`DC-019`) must support direct mobile camera capture (`accept="image/*,application/pdf" capture="environment"`) with automatic client-side image compression (`< 800KB`) so partners on rural 3G networks can upload PAN/Registration certificates without upload timeouts.

### 31.3 Low-Bandwidth Rural 3G/4G Performance & Progressive Map Fallback
To guarantee usability along mountain highways and rural districts:
1. **Lightweight Interactive SVG Vector Map First (`DC-009`):**
   - The 7-Province and 77-District Explorer (`M10`) must render an instant, zero-external-tile interactive SVG vector map of Nepal (`< 45KB` gzipped) for immediate province/district selection, only loading heavy street/topographic map tiles on explicit user zoom or `"Open Detailed Street/Topo Map"` action.
2. **Skeleton Shimmer & Text-First Priority:**
   - Critical text (Destination safety advisories, permit fees, emergency contacts, inquiry status) must render in the initial HTML/JSON payload (`< 50KB`) before high-resolution photography finishes loading.
